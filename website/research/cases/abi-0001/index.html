When a wheel requires newer C++ symbols than its target provides

A static comparison of CasADi 3.8.0 and 3.8.2 ARM64 Linux wheels.

Abstract

A published CasADi 3.8.0 ARM64 Linux wheel was reported to fail imports on some older Linux systems because its native extension required GLIBCXX_3.4.32. We downloaded the published 3.8.0 and 3.8.2 wheels, verified each against its official PyPI SHA-256 digest, and inspected the ELF version requirements of casadi/_casadi.so without executing the wheel. The highest observed requirement fell from GLIBCXX_3.4.32 to GLIBCXX_3.4.21. This demonstrates a specific change in static binary requirements—not a full deployment compatibility proof or an independently blinded EnvGuard diagnosis.

1. Original upstream failure report

In CasADi issue #4402, a user reported that the 3.8.0 manylinux_2_28_aarch64 wheel could not import on Ubuntu 22.04 ARM64 because the system libstdc++ did not export GLIBCXX_3.4.32. The report included ELF version-inspection results and described a working alternative environment.

The maintainer acknowledged the defect, and later reported a repaired nightly build. The issue reporter subsequently confirmed successful execution with that nightly wheel. These are upstream reports, not results of our own runtime verification.

2. Static artifact-inspection design

Our experiment does not try to reproduce the original ARM64 import crash on an x86-64 CI runner. Instead, it measures the required symbol-version metadata in the exact published wheels. The target is the same cp310-none-manylinux_2_28_aarch64 platform tag for both versions.

  1. Request official PyPI release metadata for 3.8.0 and 3.8.2.
  2. Download only the exact wheel corresponding to the registered ARM64 platform, without installing its contents.
  3. Verify the byte size and SHA-256 against PyPI metadata.
  4. Extract only casadi/_casadi.so with size limits into temporary storage.
  5. Run readelf --version-info and record required GLIBCXX symbol versions.
  6. Compare the highest required versions and publish a bounded JSON result.

The initial analysis used a dedicated research script. A new experimental CLI on the current source branch, inspect-wheel-abi, now inspects the same selected ELF objects using its general static-analysis path. Both approaches avoid dynamic library loading; the original archived v1.0rc2 wheel did not contain the new command.

Observed change

The maximum required GLIBCXX symbol version in the selected native extension declined between the two published wheels. That change is consistent with improved compatibility with older C++ runtimes, but actual imports were not tested here.

The hosted workflow completed successfully. It produced a machine-readable artifact retained by GitHub for a limited period. A permanent summarized evidence record preserves the observed requirements, SHA-256 digests, run URL and limitations.

New supported CLI regression: A later hosted EnvGuard CLI run independently scanned these exact two public wheels through envguard-ci inspect-wheel-abi --member casadi/_casadi.so, again observing GLIBCXX_3.4.32 and GLIBCXX_3.4.21. The permanent CLI record preserves wheel hashes and measured requirements. This is still a disclosed, nonblind static test, not a target-runtime import demonstration.

4. Reproducing the static inspection

The script requires a Linux runner with readelf and network access to PyPI for the exact pinned wheels. It runs no third-party Python package code.

From the ENV-Guard repository
python research/replay_native_abi.py \
  --out research-results/native-abi.json
python research/validate_native_abi.py \
  --input research-results/native-abi.json

The workflow runs on Ubuntu 24.04 with Python 3.12 and publishes a bounded, versioned evidence artifact. Nothing is installed from the inspected wheels.

5. Threats to validity and boundaries

  • One ELF member. We inspected _casadi.so; uninspected native members could still impose newer requirements.
  • No target machine. We did not run a Python import on ARM64 Ubuntu 22.04 or inspect that machine's actual libstdc++.
  • Static references. readelf shows recorded symbol versions; it does not resolve every runtime-loaded dependency or establish successful plugin execution.
  • Known public case. The issue and subsequent fix were available before this experiment. It cannot enter a blinded evaluation.
  • Research versus product. A successful standalone ABI investigation does not mean EnvGuard's CLI now diagnoses every manylinux compatibility issue.
  • CI scope. This source issue is primarily a user-reported compatibility problem. Its eligibility as an independent *CI* incident remains unverified.
