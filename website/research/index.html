Research & benchmarks

A reproducible evaluation of Python CI failure diagnostics—with an explicit separation between synthetic fault injection, hosted CI evidence, and independent field accuracy.

Abstract

EnvGuard CI has demonstrated exact matches to known developer-injected fault labels in a controlled offline laboratory. It has also operated on hosted CI runners, including a deliberately incorrect Python interpreter. These observations support further evaluation; they do not establish general causal accuracy, superiority over package managers, or enterprise readiness. This page reports what has been measured, explains how to reproduce it, and defines the independent benchmark required before broader performance claims.

Claim discipline. All published numerical outcomes below originate from the committed sample run. No competitor benchmark has been executed and published yet.

Cases with author-known injected labels are useful for regression tests, but they provide a biased estimate of performance on unseen incidents. For a stronger claim, fault labels must be verified without relying on EnvGuard's diagnosis.

2. Controlled fault-injection study

The repository's executable lab builds local Python wheels, constructs disposable virtual environments and triggers actual subprocess failures. On Linux with a C++ compiler it also builds native shared libraries for missing-library and missing-symbol experiments.

Sampling limitation. All eleven scenarios use a closely related synthetic project, not eleven independently sampled projects. The historical metric root_cause_accuracy_at_1 = 1.0 is a legacy name; it should be cited as injected-label agreement, not field root-cause accuracy.

4. Hosted CI evidence and incident records

Case H1 — GitHub Actions controlled failure, November 2026

The initial GitHub Actions run executed a synthetic wrong-interpreter scenario and logged a No module named riskbatch error. EnvGuard reported WRONG_PYTHON_INTERPRETER. That workflow was not an unqualified success: a brittle assertion in the demo's Markdown validation failed, and an outdated release smoke-test version check failed separately. We keep that run visible because failed tests are part of the empirical record.

Case H2 — Successful GitHub quality gates

The subsequent hosted CI run completed successfully across the supported test matrix and release/lab jobs. This demonstrates integration and regression behavior on the tested runner configurations, not independent accuracy on novel failures.

Case H3 — GitLab wrong-interpreter pilot

The separate GitLab pilot repository has previously executed an intentionally failing job with two virtual environments: the package was installed in an intended environment, while the failing command used another interpreter. Its evidence report classified the wrong-interpreter failure, and GitLab retained the diagnostic artifacts. The pilot is a real hosted run of a synthetic incident, not an independently discovered production outage.

No production claims. Public real-world incident candidates from outside the project still need independent root-cause adjudication, permission to reuse evidence, and held-out evaluation. They are not silently counted as solved.

5. Comparator methodology

We propose a paired comparison with two established dependency consistency tools: pip check and uv. Both are valuable tools, but their pip check commands address installed dependency metadata consistency rather than full CI root-cause attribution. It would be unfair to score them as incorrect for not diagnosing an unexpected Python executable or a broken native loader.

The accompanying comparison runner records exit statuses, tool versions and timings on exactly the same lab virtualenvs. It focuses on the metadata-related subcases when discussing metadata-check behavior. A nonzero checker exit status is a signal, not an exact failure-cause label.

6. A held-out benchmark of real incidents

We propose an independent collection of at least 50 historical Python CI incidents across multiple maintainers and projects. Each candidate should have a failing revision, a relevant working baseline, redacted logs and an independently verified correction. Two adjudicators should review the causal label without seeing EnvGuard's prediction; disagreements should remain explicit.

  1. Register the cases. Fix inclusion criteria and an anonymous incident identifier. Keep an explicit UNKNOWN category when the evidence is insufficient.
  2. Freeze the environment. Pin tool versions, repository commits, Python interpreters, OS images and permitted artifacts. Reset the environment between trials.
  3. Predeclare scope. Distinguish general application failures from package metadata issues and environment/ABI failures. Report coverage separately from accuracy.
  4. Blind the evaluator. Withhold fixing commits and reviewer labels from the tool and from human operators measuring investigation time.
  5. Measure both correctness and harm. Record correct attribution, unsupported attribution, abstention, evidence quality, runtime and time-to-diagnosis.
  6. Publish the failures too. Retain anonymized per-case results and study deviations, not only headline means.

7. Evaluation metrics

For eligible, independently labeled cases, report:

Primary endpoint

Correct attribution@1 = (independently verified exact-cause predictions) / (independently labeled in-scope incidents).

MetricPurpose
In-scope attribution@1Exact labels on eligible cases; report a confidence interval
CoverageFraction of all sampled incidents a tool claims to support
Unsupported attribution rateWrong environmental causes asserted on negative controls
Abstention rateFrequency of explicit uncertainty rather than unsupported guesses
Evidence fidelityHuman-reviewed proportion of claims linked to reproducible observations
Paired investigation timeHuman time to a correct diagnosis with randomized tool order

Tool execution time alone does not approximate the time saved for an engineer. Confidence intervals must reflect the sample size and repeated incidents from the same project.

8. Reproducing the experiments

The following workflow is designed for a local checkout or disposable CI runner. Use a Linux machine with a C++ compiler to include native cases; inspect the skip counter on other platforms.

Step A · Generate the injected-fault lab (local artifacts only)
git clone https://github.com/zgcharaf/ENV-Guard.git
cd ENV-Guard
python -m pip install -e .
python lab/run_lab.py --out research-results/lab
python -m json.tool research-results/lab/benchmark.json
Step B · Optional paired metadata checks
python -m pip install uv
python research/compare_tools.py \
  --lab-output research-results/lab \
  --out research-results/comparison.json \
  --require-uv

This optional runner must be executed before reporting any comparator figures. It inspects the disposable environments without modifying packages, disables package-index lookups and stores hashed outputs, statuses and tool versions. Version-specific command support should be checked before treating any tool failure as meaningful.

Step C · Preserve the environment and revision
git rev-parse HEAD
python --version
python -m pip --version
uv --version

For full methods, data fields, and interpretation, see the research protocol.

9. Threats to validity

Construct validity. The injected failure label is known in advance and may correlate with the diagnostics already implemented. External validity. Most cases share a single synthetic Python project and do not represent public-package, private-index, cross-language or enterprise production complexity. Measurement validity. The recorded 19.7 seconds is total lab execution time, not a cross-tool speed advantage. Comparability. A dependency consistency checker is not an incident classifier and should not be evaluated with the wrong target metric.

Security and research ethics. Real incidents can disclose dependency inventories, internal repository names and credentials. No sensitive employer data or raw private logs should be published without authorization. Independent labels may remain uncertain even after a patch is merged.

10. Contribute a reproducible incident

Submissions should contain a minimal project, failing and working execution context, redacted observed logs, the adjudicated explanation (with supporting evidence) and permission to redistribute. An issue describing only an error message is a candidate for investigation, not a ground-truth benchmark item.
