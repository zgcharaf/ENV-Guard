2. Independent evidence review

Before a candidate becomes a scored incident, the team must confirm the actual failed CI run and revision, establish a comparable good state, identify the correcting change and obtain a successful post-fix run where possible. Two reviewers should independently assess the facts before seeing any EnvGuard hypothesis.

  1. Verify the GitHub source issue and a reproducible failing job; reject non-CI cases from the main cohort.
  2. Check previous comparable environments, dependency metadata and available CI artifacts.
  3. Deduplicate multiple failed jobs with the same underlying change.
  4. Freeze a blinded diagnostic bundle excluding fixing commits and resolution text.
  5. Record two independent evidence-led reviews; adjudicate disagreements and retain unknowns.
  6. Only then add it to a sealed, versioned held-out evaluation set.

The complete protocol and blank review form are published for auditability.

3. Data leakage and selection bias

Issue closure is not sufficient evidence of a fix. The same project may contribute many correlated failures; external search terms favor already-documented problems. Independent performance must be calculated on a genuinely held-out set whose labels and solution commits were not available during diagnosis.

Data safety. Never publish unredacted CI logs, credentials, employer build details, package registry secrets or private repository identifiers. Discovery does not require executing issue attachments or arbitrary code.

4. Next milestone

Our goal is at least 50 deduplicated and independently adjudicated incidents spanning multiple Python CI projects and failure classes. Until that stage, the research section reports developer-injected labels and hosted synthetic experiments only.
