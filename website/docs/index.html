Reference manual

An evidence-led guide to diagnosing Python environment failures without conflating observation, correlation, and verified correction.

Scope

This manual documents the commands present in EnvGuard CI v1.0.0rc2. The software is an experimental release candidate for Python 3.11+. It operates locally by default; optional GitLab and GitHub baseline retrieval use their respective APIs. It is neither a package manager nor an autonomous repair system.

1. Introduction

EnvGuard CI is a command-line diagnostic tool for Python environments. It combines selected interpreter identity, installed-distribution metadata, project configuration and error signatures into reproducible JSON observations. It can compare a failing run with a supplied or fetched known-good snapshot and render an evidence-linked incident dossier.

The central distinction is between what happened (for example, Python could not import a module) and what caused it (for example, an unintended interpreter was invoked). EnvGuard assigns a specific cause only when supporting evidence is present. Otherwise the incident remains unresolved.

Compatibility. Uses existing pip, uv, Poetry and virtual environments. It does not resolve or install application dependencies unless you explicitly wrap an installation command.

2. Installation

Requirements

  • CPython or another compatible Python runtime at version 3.11 or newer.
  • Git and a working Python installer (python -m pip) to install from source.
  • Internet access to clone or obtain the repository and install its packaging dependency, unless these are available offline.
  • Docker only for certify-wheel and optional Linux-container experiments.

Linux, macOS, WSL2

Shell
git clone https://github.com/zgcharaf/ENV-Guard.git
cd ENV-Guard
python -m pip install -e .
envguard-ci --version

Windows PowerShell

PowerShell
git clone https://github.com/zgcharaf/ENV-Guard.git
cd ENV-Guard
py -m pip install -e .
envguard-ci --version

For CI or repeatable installation, use a vetted wheel built from a reviewed commit instead of an editable checkout. The release checklist covers wheel and source-distribution validation.

Package naming. The distribution, executable and import name are envguard-ci, envguard-ci and envguard_ci, respectively. Do not substitute the unrelated envguard package. Public PyPI availability is not asserted here.

3. Core concepts

Snapshot

A snapshot is a normalized, versioned JSON document recording a target interpreter, installed distributions, project metadata, platform identifiers and optional native-library inspection results. It does not record all filesystem contents or prove that the application can execute.

Fingerprints

The spec fingerprint summarizes selected declarative inputs and the runtime fingerprint summarizes observed runtime metadata. An artifact fingerprint may be unavailable; do not treat a metadata fingerprint as a cryptographic attestation of installed binary bytes.

Baseline

A baseline is an explicitly supplied snapshot or a successful-run artifact fetched from GitLab/GitHub. Before comparing, check OS, architecture, interpreter implementation, Python minor version and ABI. A successful workflow is not necessarily the preceding commit or a causal control.

Finding, hypothesis and proof

TermMeaning
ObservationDirectly captured outcome, error signature, interpreter identity or metadata.
FindingAn inconsistency or difference supported by checks; not necessarily the failure cause.
HypothesisAn explanation supported to some degree by the available evidence.
ExperimentRerun the same command with an explicitly changed condition; record both outcomes.
Bounded verificationA particular command passed in a particular candidate environment, not universal compatibility.

4. Architecture

The implementation is a local Python package. Its major subsystems are: collection (runtime observation), graph and requirements (installed metadata and markers), comparability and diagnostics (snapshot differences), failure and incident (evidence-led analysis), gitlab and github (read-only CI artifact retrieval), and artifacts, verification, certify (specific integrity and execution tests).

Processing sequence

Run command → collect or inspect evidence → compare compatible snapshots → classify observed failure → render the evidence ledger → optionally execute a separately authorized experiment.

No central database or EnvGuard telemetry endpoint is required. The wrapped application command still executes with the runner's privileges, and CI reports remain subject to the hosting platform's access controls.

5. Your first diagnosis

Capture, check, run
envguard-ci snapshot --project . --out local.json
envguard-ci doctor --snapshot local.json
envguard-ci investigate --project . \
  --snapshot-out current.json --report-out incident.json \
  -- python -m unittest discover -s tests

EnvGuard saves the JSON report and, when possible, an adjacent Markdown dossier (for example, incident.md). The underlying command's original failure exit status is preserved. For a Windows-specific walkthrough and a deliberately failing example, see Tutorial 1.

7. Inspecting and comparing environments

snapshot

Capture target interpreter
envguard-ci snapshot --project . --python .venv/bin/python \
  --out baseline.json

--python selects which interpreter to inspect; without it, EnvGuard inspects the interpreter running the tool. Linux --native enables selected ELF and shared-library checks; without it, native evidence is not gathered.

doctor

Check declared/observed requirements
envguard-ci doctor --snapshot baseline.json --format text
envguard-ci doctor --snapshot baseline.json --extra dashboard

The --extra flag activates named project extras; unselected extras should not be counted as missing required dependencies.

graph

Focused dependency reasoning
envguard-ci graph --snapshot baseline.json --focus pandas
envguard-ci graph --snapshot baseline.json --scope environment
envguard-ci graph --snapshot baseline.json --show-inactive

By default the graph focuses on project-reachable dependencies. Environment scope includes the installed environment; --show-inactive displays conditional and unselected references for explanation.

diff

Known-good vs current
envguard-ci diff --baseline baseline.json --current current.json \
  --format json --out difference.json

A change in runtime fingerprint is evidence of drift, not a causal diagnosis. The --fail-on threshold can make findings affect the command exit code; absent that threshold, run outcomes and diagnostic severity are separate.

8. Investigating CI commands

ci-run — explicit baseline

Run tests through the intended interpreter
envguard-ci ci-run --project . --python .venv/bin/python \
  --baseline baseline.json \
  --snapshot-out incident/current.json \
  --report-out incident/report.json \
  -- .venv/bin/python -m pytest -q

The argument after -- is the command to execute, not a shell command line. Use a direct Python invocation where possible: arbitrary shell wrappers, subprocesses, uv run and poetry run are not traced to the eventual Python child.

investigate — optional fetched baseline

GitLab example
envguard-ci investigate --project . --python .venv/bin/python \
  --last-green gitlab --baseline-ref "$CI_DEFAULT_BRANCH" \
  --baseline-job 'envguard-ci:tests' \
  --baseline-artifact envguard-ci.json \
  --snapshot-out incident/current.json \
  --report-out incident/report.json \
  -- .venv/bin/python -m pytest -q

If the requested baseline cannot be fetched, EnvGuard can continue with an explicitly incomplete comparison. Use --require-baseline to refuse the wrapped execution when the baseline is unavailable. --fail-on changes the diagnostic threshold policy; do not conflate diagnostic severity with the wrapped command's return code.

diagnose-failure — existing logs

Historical failure review
envguard-ci diagnose-failure --baseline baseline.json \
  --current current.json --log failure.log \
  --exit-code 1 --format json --out diagnosis.json

Logs are treated as untrusted observations. A matching error string alone is not proof of a root cause. Avoid exporting raw logs containing secrets.

9. Incident dossiers and reporting formats

A normal instrumented run emits a snapshot, a diagnostic JSON report, and an adjacent Markdown incident dossier. The JSON provides the supporting evidence references used by the Markdown report.

OutputTypical contents
current.jsonPython version, interpreter identity, project metadata, installed distribution inventory and fingerprints.
report.jsonCI execution result, compatible-baseline status, findings, observed failure and root-cause hypothesis, if supported.
report.mdHuman-readable evidence ledger, confidence, limitations and safe next checks.
Render an existing report
envguard-ci triage --report report.json \
  --format markdown --out dossier.md
envguard-ci render-report --input report.json \
  --format github-annotations
envguard-ci render-report --input report.json \
  --format gitlab-codequality --out codequality.json

Code Quality anchoring. Environment-wide findings may use a synthetic repository-relative anchor such as pyproject.toml:1. This does not mean that line contains the defect.

Interpreting diagnostic language

Report termCorrect reading
no_local_findingsNo inconsistency found by implemented checks, not proof the command succeeded or the environment is sound.
drift_detectedComparative differences found; they might be unrelated to the failure.
supported_hypothesisObservations support one explanation; not independently verified causation.
unresolvedInsufficient evidence to assign a specific underlying cause.
observed_candidate_succeedsOne alternate interpreter invocation succeeded after the original failed; scope is limited to those runs.

10. GitLab and GitHub baselines

EnvGuard may retrieve the latest successful run's snapshot from a named GitLab job or GitHub Actions artifact. The baseline is a historical reference, not necessarily the immediate predecessor of the failing commit.

GitLab

Explicit read-only baseline retrieval
envguard-ci gitlab-baseline \
  --job 'envguard-ci:tests' \
  --artifact envguard-ci.json \
  --out good.json

Inside a runner, GitLab usually supplies CI_API_V4_URL, CI_PROJECT_ID, and CI_DEFAULT_BRANCH. Authentication may use CI_JOB_TOKEN if permitted, or a narrowly scoped ENVGUARD_GITLAB_READ_TOKEN passed through protected variables. Use artifacts: when: always for failure reports and a separately retained green snapshot.

GitHub Actions

Explicit GitHub baseline retrieval
envguard-ci github-baseline --repo OWNER/REPO \
  --ref main --workflow ci.yml \
  --artifact-name envguard-baseline \
  --snapshot-name envguard-ci.json --out good.json

Provide a read-authorized GITHUB_TOKEN or ENVGUARD_GITHUB_READ_TOKEN, and grant actions: read in the workflow. The baseline-producing job must upload a snapshot file within an artifact named envguard-baseline. Do not expose privileged tokens to untrusted fork pull requests.

Comparability warning. OS, architecture, Python version/implementation and ABI should be comparable; otherwise a dependency difference may simply reflect platform-specific resolution. A baseline from an unrelated runner is not a scientific control.

Complete end-to-end setup: GitLab tutorial and GitHub Actions tutorial.

11. Wheel identity and target compatibility

inspect-wheel

Offline byte and RECORD verification
envguard-ci inspect-wheel \
  --wheel dist/example-1.0.0-py3-none-any.whl \
  --out integrity.json

To compare against a trusted known SHA-256, add --approved-sha256 followed by the expected 64-hex-character digest. This checks archive identity and internal RECORD hashes. It does not establish publisher trust, system-library compatibility, or runtime behavior.

certify-wheel

Offline target-container import smoke
envguard-ci certify-wheel \
  --wheel dist/example-1.0.0-py3-none-any.whl \
  --image 'registry.example/runtime@sha256:REPLACE_WITH_REAL_64_HEX_DIGEST' \
  --module example --wheelhouse ./approved-wheels \
  --out deployment-proof.json

The example image digest is a placeholder. Use a real pre-pulled, trusted image pinned by immutable digest. EnvGuard attempts installation using local artifacts and runs a Python import test with Docker networking disabled. Other dependencies must already be available in the approved wheelhouse or target image. Mutable tags require explicit --allow-mutable-image.

Execution risk. Wheel installation and imports execute package code. Docker's isolation is limited; use approved images and trusted artifacts on disposable hosts. A passing import smoke test does not certify production behavior or security.

12. Constrained correction experiments

The verify-interpreter command compares the same module invocation under two explicitly named Python environments. It requires an opt-in flag and does not patch source files, change installed dependencies or run inside a security sandbox.

Only in a trusted/disposable environment
envguard-ci verify-interpreter --project . \
  --original-python .venv-bad/bin/python \
  --candidate-python .venv-good/bin/python \
  --allow-local-execution \
  --out experiment.json -- -m app

The command requires a directly specified Python -m or -c invocation, distinct observable environments and a bounded timeout (default 60 seconds). The candidate is not run if the original command unexpectedly succeeds or fails to launch.

Critical limitation. Changing the interpreter often changes the installed packages too. A successful candidate run is evidence that the selected candidate environment executes the command; it does not isolate interpreter identity as the sole causal factor.

13. JSON data, fingerprints and schemas

Runtime observations and reports are versioned JSON documents intended for machine analysis. The repository contains environment snapshot schema v1 and dependency graph schema v2.

Fields commonly encountered in a snapshot include schema_version, platform, runtime, packages, project, native and fingerprints. Reports include ci, counts, findings, failure_analysis, and sometimes execution_provenance.

Inspect key report fields
python -c "import json; d=json.load(open('report.json')); print(d.get('status')); print(d.get('failure_analysis', {}).get('root_cause_hypothesis'))"

Do not treat hashed or redacted paths as reconstructible full filesystem identities. Tokens and full raw logs are deliberately not included in regular diagnostic JSON, but private package names, version information and project identifiers can remain sensitive.

14. Security and privacy model

What is local

Snapshot generation, graph inspection, comparisons, offline wheel inspection and dossier rendering do not require an EnvGuard cloud service. CI baseline retrieval uses GitLab/GitHub APIs when explicitly requested. Diagnostic tools do not guarantee that application code or import hooks cannot run during interpreter probing or wrapped execution.

Protected inputs and outputs

  • Use private repositories, scoped artifact permissions and short report retention for proprietary software.
  • Never embed PATs, registry passwords or customer data in commands or tracked files.
  • Protect source, test and CI artifacts from unauthorized readers: metadata itself may be confidential.
  • Do not run arbitrary pull-request code in a privileged repair environment with secrets or write tokens.
  • Treat all fetched JSON, package metadata, log text and wheel contents as untrusted inputs.
  • Pin container images by digest; avoid handing the Docker socket to untrusted code.

Review SECURITY.md for disclosure guidance. A local-first architecture does not by itself imply compliance with banking security requirements.

15. Troubleshooting

envguard-ci is not recognized.

Use python -m envguard_ci --version from the installed interpreter, or confirm the environment's Scripts/bin directory is on your PATH. Install from the source checkout with python -m pip install -e .. Remove stale PYTHONPATH overrides.

It reports no_local_findings although tests failed.

The tool may have observed the failed command but found no supported environment inconsistency. Inspect failure_analysis and the Markdown dossier. A failed command and a clean local doctor are not contradictory.

Baseline fetch says unavailable.

Verify branch, exact CI job/workflow and artifact names, permission scopes, artifact expiration and success status. On a first run there may be no successful baseline. Use --require-baseline only if a missing baseline should block execution.

Why is wrong interpreter diagnosis missing?

Set --python to an explicitly intended executable and invoke Python directly after --. EnvGuard does not trace arbitrary shell wrappers or spawned child Python processes.

Hundreds of “optional” package references appear.

Package metadata can list unselected extras and marker-excluded requirements. Use a project-focused graph and avoid treating raw references to uninstalled packages as missing required dependencies. Compare with python -m pip check on the same interpreter.

The Docker certification command fails.

Check that Docker Engine is running, the target digest exists locally, the container can run Python and venv, and all required wheels are available without network access. The default offline image requirement is deliberate.

What does an exit code tell me?

ci-run and investigate preserve the wrapped command's failure exit status in normal operation. Nonzero may also occur because of CLI usage, inaccessible resources or a configured diagnostic --fail-on policy. Always inspect the report and command log; do not infer one universal exit-code mapping.

16. Development and contribution

From the project root
python -m pip install -e .
python -m unittest discover -s tests -v
python lab/run_lab.py
python examples/run_v1_repair_demo.py

The optional Linux C++ lab can be executed with Docker by building lab/Dockerfile. The lab intentionally injects failures and is not a blind industry benchmark. For contribution standards see CONTRIBUTING.md; for known changes see the changelog.

A useful external contribution is a minimal, anonymized reproduction of a CI environment failure, with a compatible working run, a failing run, and a clear independent root-cause label. Do not submit confidential bank logs or credentials.

18. Experimental native wheel ABI inspection

The latest main source branch contains an opt-in inspect-wheel-abi CLI for static ELF inspection. This experimental command was added after the previously built v1.0.0rc2 wheel and should not be claimed to be part of that archived release artifact.

It reuses the wheel SHA-256 / RECORD integrity checks and reads ELF architecture, DT_NEEDED providers and exact GLIBC, GLIBCXX, and CXXABI version needs with GNU readelf. The wheel is not installed, imported or executed.

Capture candidate target library exports

Run on the intended Linux target
envguard-ci capture-native-target \
  --out target-native.json

The manifest records exact version definitions and hashes from selected local ldconfig provider candidates. It does not prove which libraries a specific application process will load.

Inspect a wheel and compare with a target

Static examination
envguard-ci inspect-wheel-abi \
  --wheel dist/your_project.whl \
  --target-manifest target-native.json \
  --out wheel-abi.json \
  --fail-on-shortfall

With the optional --fail-on-shortfall flag, an observed required symbol-version label missing from a named target provider causes exit code 1. Without a target manifest, the report says target_not_provided; an unobserved provider or mismatched architecture is explicitly unknown, not compatible.

Boundary. Parsing an ELF file with readelf is not a security sandbox; use a disposable unprivileged runner for untrusted artifacts. Static symbol observations cannot certify import success, manylinux policy compliance or production safety.

Read the complete native-ABI manual, follow the worked tutorial, and see the separately sourced CasADi static ABI case.
