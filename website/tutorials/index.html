Worked tutorials

Eight reproducible exercises, moving from a local interpreter snapshot to evidence-led CI incident analysis and bounded correction experiments.

How to use this guide

Each exercise distinguishes its expected observation from what that observation proves. Start with the local tutorial. The GitLab and GitHub exercises use public example configurations that must be adapted to your application's build system and access controls. Use only synthetic or approved code in the repair and container exercises.

Prerequisites

Clone the current repository and install it from source. This is not a PyPI installation instruction.

Linux / macOS / WSL2
git clone https://github.com/zgcharaf/ENV-Guard.git
cd ENV-Guard
python -m pip install -e .
envguard-ci --version
Windows PowerShell
git clone https://github.com/zgcharaf/ENV-Guard.git
cd ENV-Guard
py -m pip install -e .
envguard-ci --version

The CLI should report envguard-ci 1.0.0rc2 for this release. If you are using a later checkout, trust the installed --version result and inspect its help text for changes.

Safety. ci-run and investigate execute your command. verify-interpreter executes an application twice after explicit opt-in. These are not secure sandboxes. Avoid production credentials and data in demonstrations.

1. Local environment diagnosis

Objective. Determine which Python environment is active, inspect installed dependencies and generate a machine-readable record.

Capture a snapshot

From the repository root
envguard-ci snapshot --project . --out local.json

This creates local.json with runtime, platform, distribution and project information. Without an explicit --python argument, the inspected Python is the one running EnvGuard.

Inspect the graph and check requirements

Diagnose the snapshot
envguard-ci doctor --snapshot local.json
envguard-ci graph --snapshot local.json
envguard-ci graph --snapshot local.json --scope environment

The second graph command examines all installed distributions, whereas the default view is project-oriented. Optional dependencies whose extras are not selected should not be misreported as broken requirements.

Check independently

Cross-check with pip
python -m pip check

Expected. A snapshot file and diagnostic summary. no_local_findings indicates no inconsistency was detected by implemented checks; it does not certify that every import works.

Next exercise. In Tutorial 2, a real module import will fail even though the correct environment has the required package.

2. Reproduce a wrong-interpreter failure

Objective. Distinguish an undeclared dependency from the same symptom caused by executing the wrong virtual environment.

Run the controlled failure lab

Platform independent
python examples/run_failure_demo.py

The script constructs tiny wheels locally, creates disposable virtual environments under lab/.envguard-runs, installs the example package in the intended environment and runs the application with a different Python executable.

Inspect the diagnostic files

Linux / macOS / WSL2
cat lab/.envguard-runs/demo-ci-report.md
python -m json.tool lab/.envguard-runs/demo-ci-report.json
Windows PowerShell
Get-Content .\lab\.envguard-runs\demo-ci-report.md
Get-Content .\lab\.envguard-runs\demo-ci-report.json -Raw

Expected. The failing command returns nonzero; EnvGuard records WRONG_PYTHON_INTERPRETER when the expected and executed interpreter identities and missing-package evidence support it. The demo runner itself exits zero when those assertions pass.

Interpretation. A confirmed direct interpreter mismatch plus the package's presence only in the intended runtime is stronger evidence than the words No module named ... alone.

Run all supported synthetic cases

Failure laboratory
python lab/run_lab.py

On native Windows, Linux-only C++ shared-library tests may be skipped. To run them, use a Linux runner or Docker Desktop in Linux mode; see lab documentation.

3. Integrate with GitLab CI/CD

Objective. Retain a diagnostic dossier even when a project test fails, and optionally compare it against a successful default-branch snapshot.

Prepare a safe project runner

Use a private test repository or approved sandbox. Start with a Python project that has requirements.txt and tests/. The example below checks out the EnvGuard source, creates an application virtualenv, instruments test execution and retains diagnostic artifacts. Pin the tool checkout to a reviewed commit for production use instead of relying on a moving main branch.

Adapted .gitlab-ci.yml
stages: [test]

python:tests:
  stage: test
  image: python:3.12-slim
  script:
    - git clone --depth 1 https://github.com/zgcharaf/ENV-Guard.git tools/envguard-ci
    - python -m pip install -e tools/envguard-ci
    - python -m venv .venv
    - .venv/bin/python -m pip install -r requirements.txt
    - |
      envguard-ci ci-run --project . --python .venv/bin/python \
        --snapshot-out incident/current.json \
        --report-out incident/report.json \
        -- .venv/bin/python -m unittest discover -s tests
  artifacts:
    when: always
    expire_in: 7 days
    paths:
      - incident/current.json
      - incident/report.json
      - incident/report.md

The runner must have git and network access to the source repository and package index. Test the installation step and your existing tests separately; the sample instruments only execution after dependencies are installed. To capture installer failures as well, wrap that installation with another ci-run invocation and give it distinct report paths.

Produce the first healthy baseline

For automatic retrieval, the successful default-branch job should upload the snapshot under a stable artifact path, such as envguard-ci.json. Keep its name and job identity consistent across runs. A first or isolated pipeline may have no baseline, which is expected.

Successful snapshot
envguard-ci snapshot --project . \
  --python .venv/bin/python \
  --out envguard-ci.json

Use a historical baseline

GitLab job with authorized artifact access
envguard-ci investigate --project . \
  --python .venv/bin/python \
  --last-green gitlab \
  --baseline-ref "$CI_DEFAULT_BRANCH" \
  --baseline-job "python:tests" \
  --baseline-artifact envguard-ci.json \
  --snapshot-out incident/current.json \
  --report-out incident/report.json \
  -- .venv/bin/python -m unittest discover -s tests

Historical artifact access depends on GitLab settings and runner permissions. The default CI_JOB_TOKEN may not be authorized; use a protected, narrowly scoped ENVGUARD_GITLAB_READ_TOKEN only if needed. Where no historical baseline is available, EnvGuard records that limitation instead of fabricating a comparison.

Acceptance check. Intentionally break a disposable job with the wrong interpreter. Confirm that the job remains failed while GitLab uploads incident/report.json and incident/report.md as artifacts. Do not upload sensitive logs, tokens or production package inventories to public artifacts.

See the project's own GitLab pipeline and smaller integration snippet for starting configurations.

4. Integrate with GitHub Actions

Objective. Instrument a test job, upload reports even when it fails, and optionally compare it with a prior successful Actions artifact.

Add the basic workflow

.github/workflows/python-envguard.yml
name: Python diagnostics
on: [push, pull_request]
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - name: Install EnvGuard
        run: |
          git clone --depth 1 https://github.com/zgcharaf/ENV-Guard.git tools/envguard-ci
          python -m pip install -e tools/envguard-ci
      - name: Install project
        run: python -m pip install -r requirements.txt
      - name: Run tests with diagnostics
        run: |
          envguard-ci ci-run --project . --python "$(command -v python)" \
            --snapshot-out current.json \
            --report-out incident.json \
            -- python -m unittest discover -s tests
      - name: Save incident reports
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: envguard-diagnostics
          path: |
            current.json
            incident.json
            incident.md
          if-no-files-found: warn

Review and pin external actions and EnvGuard source revision for security-sensitive pipelines. This example uses a standard Python test layout; adapt the installation and test commands to your project.

Optional last-green lookup

The read-only fetcher needs a successful workflow run on the target branch with an artifact named envguard-baseline that contains a snapshot named envguard-ci.json. Grant actions: read in the workflow job and pass the GitHub token only to authorized internal runs.

Investigate with GitHub baseline
envguard-ci investigate --project . \
  --python "$(command -v python)" \
  --last-green github \
  --github-workflow python-envguard.yml \
  --baseline-ref main \
  --github-artifact envguard-baseline \
  --baseline-artifact envguard-ci.json \
  --snapshot-out current.json --report-out incident.json \
  -- python -m unittest discover -s tests

The latest successful workflow artifact might be from a different change than the failing commit's parent. A difference between snapshots is not automatically causal. See the working project workflow for baseline artifact production and permission details.

Acceptance check. Confirm that the source installation and tests succeed on your supported Python versions, that a deliberately failing branch uploads its report, and that baseline retrieval explicitly indicates when an artifact is missing or inaccessible.

5. Verify Python wheel integrity

Objective. Check the bytes of a built wheel before distributing it, without importing or executing code during the inspection step.

Build a real example wheel

Local packaging
python -m pip install build
python -m build --wheel

This builds the repository's own wheel into dist/. Verify the name shown in the output before copying the command below.

Inspect the wheel archive

Current rc2 artifact
envguard-ci inspect-wheel \
  --wheel dist/envguard_ci-1.0.0rc2-py3-none-any.whl \
  --out integrity.json

The inspection records the archive hash, internal RECORD checks, potentially native members and tag compatibility information. Compare with a hash from a trusted independent source using --approved-sha256 when available.

Optional offline container smoke test

Only use trusted wheels and a pinned, approved Linux Python image. First pull the image through a permitted workflow and obtain its actual immutable digest. Then verify the wheel in that image:

Example — replace digest and wheelhouse with real values
envguard-ci certify-wheel \
  --wheel dist/envguard_ci-1.0.0rc2-py3-none-any.whl \
  --image 'python:3.12-slim@sha256:REPLACE_WITH_REAL_64_HEX_DIGEST' \
  --module envguard_ci \
  --wheelhouse ./approved-wheels \
  --out deployment-proof.json

Use a compatible local wheelhouse for any missing dependencies, including packaging when it is not already available in the image. The verifier operates without container network access. A passing import is a smoke check, not a security certification, full deployment validation or guaranteed ABI compatibility.

6. Verify a proposed interpreter correction

Objective. Move beyond an explanation by recording an actual failing and successful run. This experiment executes application code, so use only a disposable test project.

Run the complete local exercise

Windows, Linux, macOS
python examples/run_v1_repair_demo.py

The helper creates isolated environments, injects a wrong-interpreter failure and invokes EnvGuard's candidate experiment against the same application module. The demo prints the resulting evidence file path; the default result in this repository is lab/.envguard-runs/v1-repair-proof.json.

Inspect the recorded evidence

Linux / macOS / WSL2
python -m json.tool lab/.envguard-runs/v1-repair-proof.json
Windows PowerShell
Get-Content .\lab\.envguard-runs\v1-repair-proof.json -Raw

Expected. original.exit_code is nonzero; candidate.exit_code is zero; status is observed_candidate_succeeds; automatic_changes_made is false. Exact fingerprints will vary by machine.

Underlying command

In a real disposable project with two distinct pre-created interpreters, the direct verification interface is:

Unix example — only in disposable test environments
envguard-ci verify-interpreter \
  --project . \
  --original-python .venv-bad/bin/python \
  --candidate-python .venv-good/bin/python \
  --allow-local-execution \
  --timeout 60 --out repair-proof.json \
  -- -m app

Limitation. The two environments can differ in installed packages as well as interpreter path. The experiment verifies that the candidate invocation succeeds, not that the choice of executable was isolated as the sole cause. EnvGuard does not edit dependencies or application code.

7. Interpreting the evidence dossier

Objective. Distinguish a classified error from a supported root-cause claim, and distinguish a successful test from production readiness.

Render an incident as Markdown

Existing diagnostic JSON
envguard-ci triage --report incident.json \
  --format markdown --out dossier.md

Look for the observed failure, root-cause hypothesis, confidence, evidence ledger and limitations. The evidence ledger points back to fields in the report JSON. If the report says unresolved, do not present a speculative patch as verified.

Distinguish the possible outcomes

FindingWhat you can claim
module_missingA Python module import failed. Cause may still be unknown.
WRONG_PYTHON_INTERPRETERExpected and directly executed Python differ, supported by runtime/package evidence.
drift_detectedObserved metadata differs from the baseline; causal relevance remains to be established.
observed_candidate_succeedsThe particular tested candidate invocation succeeded after the original failed.

Report the result responsibly

A good engineering incident summary should state which command failed, which environment was inspected, which baseline was used, which observed facts support the hypothesis, what experiment was run and what remains uncertain.

Next step. Want to contribute a new failure class? Create a minimal, synthetic regression fixture and a clearly documented expected diagnosis. See the contributor guide.

8. Examine native ABI requirements without importing a wheel

Objective. Determine which versioned Linux C/C++ runtime symbols a wheel's ELF files require. Optionally compare those requirements with explicitly observed versions defined by target-runtime libraries. This is static evidence, not proof of runtime compatibility.

Install EnvGuard from the current source branch

Use the current checkout (not an earlier release wheel)
python -m pip install -e .
envguard-ci inspect-wheel-abi --help

Capture target evidence on Linux

Linux host for the intended deployment
envguard-ci capture-native-target \
  --out target-native.json

The manifest records exact exported version labels and hashes from selected ldconfig provider files. It does not guarantee that an arbitrary process will load those same providers. For a foreign ARM64 wheel, capture its target on an ARM64 Linux runtime; an x86-64 manifest is not comparable.

Inspect an existing binary wheel

Replace the wheel filename with your actual artifact
envguard-ci inspect-wheel-abi \
  --wheel dist/your_binary_package.whl \
  --target-manifest target-native.json \
  --out abi-report.json \
  --fail-on-shortfall

Expected. A JSON report with wheel SHA-256, native ELF members, DT_NEEDED libraries, provider-grouped GLIBC, GLIBCXX and CXXABI requirements, and a bounded target comparison. A missing version label yields potential_provider_symbol_gap. Unknown library or platform evidence remains unknown.

Large native wheels can be scanned one ELF member at a time using --member casadi/_casadi.so (replace with the exact member name). The command does not download, install or import the wheel.

Trust boundary. GNU readelf parses potentially untrusted binary bytes and is not a sandbox. Execute in a disposable, unprivileged CI runner. The command does not validate all manylinux policies or runtime loader behavior.

Read the full guide and the CasADi public static case study.

End of laboratory notebook. Tutorials demonstrate selected v1.0.0rc2 behaviors and intended integration patterns; they are not evidence of general accuracy on unrelated enterprise incidents. Always adapt commands to your own repository structure, shell, runner and security policy.
